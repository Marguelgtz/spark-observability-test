# Product Thesis

This document outlines the current product thesis for Spark.

## Working mission

> Spark makes software changes legible enough to automate with confidence.

*(Provisional)*

## V0 proposition

> See what every PR touches, what evidence supports it, and where your attention is needed.

## Target users

**Primary:**
* solo developers
* teams of roughly 2–20 engineers
* GitHub-centric workflows
* teams already using coding agents/automation
* organizations with little desire for enterprise governance ceremony

## User job

> "Help me quickly determine whether this change is routine or deserves more of my attention."

## Free V0 product

The free V0 product provides a GitHub Check that outlines:
* **Direct change:** What files and modules were actually modified.
* **Propagated/affected areas:** What downstream projects, workspaces, or services might break as a result.
* **CI evidence:** What tests, linters, or workflows have run against this exact change.
* **Sensitive surfaces:** Whether critical areas (auth, deployments, migrations) were touched.
* **Attention:** A deterministically evaluated LOW, MEDIUM, or HIGH attention level.
* **Transparent explanation:** Clear, human-readable reasons for why this attention level was assigned.

## Differentiation

Explicitly, the free competitor to Spark is:
> GitHub + Actions + CODEOWNERS + rulesets + custom scripts + discipline.

Spark therefore must create value through **correlation and change modeling**. We don't just list changed files; we contextualize them within the repository's topology and the available CI evidence, presenting a synthesized observability check that requires zero configuration.

## Long-term vision

*(These concepts inform the direction but will NOT be implemented in V0)*

* **Software-change evidence graph:** A unified data model linking intent, changes, evidence, and deployment outcomes.
* **Contextual autonomy:** Providing sufficient context to allow AI agents to safely take action.
* **Agent observability:** Tracking and auditing changes generated by AI actors.
* **Provider-neutral integrations:** Expanding beyond GitHub to other VCS and evidence providers.
* **Runtime outcomes:** Linking production observability (errors, performance) back to specific changes.
* **Experiential learning:** Using past outcomes to inform future change evaluations.
